# About mailstack

## What it owns

`:8195`. Centralized read/write email behind dash's Mail page, across Gmail, Outlook (Microsoft Graph) and PrivateEmail (IMAP/SMTP), with multiple accounts per provider. `GET /api/messages?account=<id>&q=<query>` hands `q` to the provider's own search (Gmail's search-box syntax: `from:unr.edu after:2023/01/01`) across every folder; a provider with no search here answers 501 rather than the unfiltered list, and `q` with `folder` is a 400. ⚠️ `PLAN.md` still says *"planning, no code yet"* and was last touched 2026-04-17, while the service is running and listening — trust the code over the plan.

Its thirteen environment variables are declared once, in `settings.go`, with llm-bridge `servicesettings`; `cmd/mailstack` reads them through that registry, and `GET /settings` describes them behind the same bearer as `/api/*`, serving a token as set or unset and never its text. A test fails on any `os.Getenv` the declarations do not name, so add a variable there first. The service owns the four names `MAILSTACK_PORT`, `MAILSTACK_DB`, `MAILSTACK_LOCAL_DB` and `MAILSTACK_TOKEN` and refuses to start on a set variable that begins with one of them and is not declared (`MAILSTACK_DB_PATH`); it does not own `MAILSTACK_`, because `MAILSTACK_URL` is what callers read to find it. The `--port`, `--db` and `--local-db` flags override their settings, and the unit passes `--port`, so the settings page shows the environment's value, not a flag's. `deploy.sh` builds the registry from the running service's environment before it stops it. `scripts/e2e-smoke.sh` asserts that the default database is absent, so run it with `HOME` pointed at an empty directory.

Local accounts also take **imported mail** — an export's messages, keyed by the id the source gave each one — for callers such as a ticket desk that must show linked messages without reading a mailbox. `POST /api/accounts/{id}/messages/import` (at most 500 messages; all or nothing; each message reports `created`, `updated` with its old and new revision, or `unchanged`) keeps text and HTML bodies separately, with absent distinct from empty, plus the Outlook store, folder and folder path, and invents no Message-ID or thread id. An optional `source {ref, sha256}` is checkpointed in the same transaction and listed by `GET /api/accounts/{id}/import-sources`, so an importer can skip unchanged export files. Reads that never touch unrelated bodies: `POST /api/messages/resolve` (at most 200 refs, by locator or by `account_id` with `provider_message_id`, one status per ref), `GET /api/messages/{id}/metadata?account=` and `GET /api/messages/{id}/body?account=&format=text|html` (raw, with an ETag, a sandboxing CSP and a 404 `code` of `message_not_found` or `body_absent`). Bodies live in `local_message_bodies`, apart from the metadata row, and `localmail/migrate.go` versions the schema with `user_version`. A lookup by `provider_message_id` must repeat `provider_message_id <> ''`, or SQLite skips the partial index and imports grow with the square of the mailbox. `go test -run TestSplitReadLatency -split-read-latency -v .` measures these reads against mailboxes of 1,000 to 50,000 messages.

An import may carry **attachments** (`attachments: [{filename, content_type, content_id, inline, source_attachment_id, content_base64}]`, at most 100 a message, none empty). Their bytes go to file-store (`FILE_STORE_URL`, `FILE_STORE_SERVICE_TOKEN` from `~/.config/file-store-tokens.env` through the host-local drop-in `mailstack.service.d/file-store.conf`); without it, an import with attachments and an attachment read answer 503. Only messages that `PlanImport` says will change are uploaded, a refused or failed import purges what it uploaded, and `PermDelete` purges a message's files before its rows. mailstack keeps which file hangs on which revision in `local_message_attachments` and never hands out a file-store id: `GET /api/messages/{id}/attachments/{a1…}?account=` checks the message first, then relays file-store's answer with its safety headers. **Revision history**: an update first copies the revision it replaces into `local_message_revisions` (metadata as served, both bodies); attachments stay under their revision's number. `GET /api/messages/{id}/revisions`, `/revisions/{n}`, `/revisions/{n}/body?format=` and `/revisions/{n}/attachments/{a…}` read them; a 404 `code` of `revision_not_found` or `attachment_not_found` says which was missing.

**Per-person access** (`principal_access.go`). A caller with the bearer and no `X-Principal-Id` is a service and unrestricted. A request naming a principal — llm-bridge-server's `/mailstack/` proxy sets it from a verified login — is checked live on every call: principal-store (an active human; an administrator passes everything), grant-store's `can_read_mail` and `can_import_mail` on resource type `mail_account` (import includes read), and kanban-store's `POST /api/entities/visible-to-principal` for messages a ticket the person may view links as `email` entity `<account>:<id>`. Message reads take the account grant or a ticket; folders, threads and lists take the account grant; import and mailbox changes take `can_import_mail`; everything else is for services and administrators (403 `route_not_open_to_principal`). An unreadable message is 404, exactly like a missing one, and resolve turns every result the person may not see into a bare `not_found`, with one kanban call per batch. The rule is strict on purpose — no mail grant reads only what tickets show — unlike grant-store's lenient default. A store that cannot answer is 502, never "holds nothing"; without the store settings (`GRANT_STORE_SERVICE_TOKEN` and `KANBAN_STORE_SERVICE_TOKEN`, from `~/.config/principal-gating-tokens.env` through the drop-in `mailstack.service.d/principal-gating.conf`) a request that names a person is 503. Every route is registered through `routeFor` with its rule, and one without a rule panics at start. Agents hold the bearer by the operator's choice and can skip all of this by calling mailstack directly.

**Pushed delivery and the outbox** (`ingress_handlers.go`, `localmail/ingress.go`). A sender such as Databricks' raw-mail custody pushes `POST /api/ingress/deliveries` (at most 100 a request) with `X-Mailstack-Ingress-Token`, a credential minted by `POST /api/ingress/credentials {source, note, account_ids}` (token shown once, only its sha256 kept; list and `…/{id}/revoke` beside it), bound to local accounts and good for nothing else. Each delivery `{delivery_id, account_id, message}` (the import message shape plus a required `source_revision`) is stored, receipted in `delivery_receipts` and announced in `message_events` in one transaction, then answered on its own: `accepted`, `replay` (that source revision with that content is already here, current or replaced), `conflict` (that source revision with different content — nothing changes, the receipt keeps the evidence), `purged`, `rejected`, or `failed` — the only one with `retry: true`. A delivery id sent again gets its first answer. Imports and deliveries share one storage command, `storeImportedMessage`, so both refuse a purged message and both write the outbox. `GET /api/events?after=&account=&limit=` is the outbox, read by cursor (`seq` is the consumer's idempotency key; events are `message.revision_available` and `message.purged`, and say nothing about tickets); `GET /api/ingress/receipts?after=&status=` is the journal. `POST /api/messages/{id}/purge?account= {"reason"}` purges files, then every revision, leaving a tombstone in `message_purges`. Nothing relays the outbox to NATS yet: no consumer on this host needs it, and a relay is a reader of `/api/events`. Out-of-order source revisions cannot be told apart from new ones, because a source revision is an opaque string: a late older revision not seen before becomes the current one.
