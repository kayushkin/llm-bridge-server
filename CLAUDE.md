# About llm-bridge-server

## What it owns

`:8160`, listening on every interface. The central session server and HTTP gateway of the llm-bridge ecosystem: it manages harness lifecycle, streams session events over SSE, holds credential bindings, and runs agent-store, memory-store, harness-store, hook-store, snapshot-store and model-store as embedded libraries. agent-store is one of them, which makes this server **the path to the host prompt source** rather than standalone agent-store on `:8300`. It also serves the service inventory and the effective-config view, so it is the single backend behind bridge-ui's whole surface. README "Routes" is the route table, generated from `routeDescriptions` and `routeAccessRules`; README "Who may call what" is the reference for who may call what.

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

# How it works

## Request authorization: every route is classified

Every request passes through `authorizeAndServe` (`internal/server/request_authorization.go`) before the mux dispatches it, and there is no way to switch that off: `config.ValidateRequestAuthorizationSettings` makes the credentials mandatory at startup. Each route is classified in `routeAccessRules`, keyed by the exact pattern it is registered under. **A pattern with no rule is 403 `route_not_classified` to everyone but the service token**, so a route added later is closed until someone decides who may call it; `TestEveryRegisteredRouteIsClassified` fails when a `HandleFunc` or `Handle` in the package has no rule, so add the rule in the same change as the route. Add its one-line description to `routeDescriptions` (`route_descriptions.go`) too, and regenerate the README table with `go test ./internal/server -run TestReadmeRouteTable -update-readme-route-table`; a test fails until both are done. Callers, in precedence order: the internal service (`X-LLM-Bridge-Service-Token` equal to `LLMBRIDGE_SERVICE_TOKEN` — unrestricted, not even held to the route table, and a wrong token is 401 rather than a silent downgrade); the internal service acting as a person (the same token plus `X-Principal-Id`, which dash sends for one of its logged-in users, and which is **401 on its own** on every route); a principal (a login cookie naming a live login session — which on any method but `GET`, `HEAD` and `OPTIONS` must also carry that session's CSRF token in `X-CSRF-Token`, else 403 `csrf_token_missing` or `csrf_token_mismatch` — or a session agent token on the store proxies only); another llm-bridge-server presenting a peer token in `X-LLM-Bridge-Peer-Token`, which acts as the peer principal the token was issued for and is held to the route rules like a person signed in as it (sent beside the service token or an `Authorization` header, 400 `ambiguous_credentials`); nobody (401 on anything that is not open or a harness callback). Whichever principal a request resolves to is read from principal-store first (`request_principal_lookup.go`): one it does not know is 400, one whose kind principal-store says does not act as a caller (`acts_as_caller` false: a group or a contact) is 400 `principal_does_not_act`, a disabled one is 403, and one it marks `is_administrator` is past every per-resource check. Sign-in (demo and Entra) still takes humans only.

## The route classes and how a handler narrows its answer

`routeOpenToEveryone`: `GET /health`, `GET /operation-types` and the sign-in routes (`POST /auth/demo-login`, `GET /auth/entra/start`, `GET /auth/entra/callback`, `GET /auth/principal`, `POST /auth/logout`, each of which checks what it needs itself). `routePrincipalManagesOwnLoginSessions` for `GET /auth/sessions` and `POST /auth/sessions/{id}/revoke`: a principal's own login sessions, anyone's for an administrator, and another person's is 404. `routeHarnessCallback`: the Claude Code and codex prehooks, the pty sidecar, `POST /hooks/exec/{id}`, the runner routes and the seed proxies — processes this server spawned, or runners, none of which carry a login, so each handler keeps whatever check it makes and nothing more. `routeOperatorOnly`: the service token or an administrator, 403 `operator_route` otherwise. `routePrincipalCreatesSession` on `POST /sessions`, where **the session is created as the calling principal whatever the body says**. `routePrincipalOwnsSession` and `routePrincipalOwnsSignal`, where a principal reaching someone else's gets **404** — the same answer as a missing one. `routePrincipalSeesOwnSessionsOnly`, where the handler narrows the answer itself. `routePrincipalReadsCatalog` for the read-only catalogs a chat UI needs. `routePrincipalRefusedCannotBeFiltered` for `GET /sessions/search`, `GET /sessions/aggregates` and `GET /snapshots/blob/{sha}`: log-store answers them across every session and a blob is shared, so a principal is refused rather than shown other people's data. `routePrincipalOrSessionAgentThroughStoreProxy` for `/kanban/` and `/grant-store/`. `routeSessionOwnerOrItsAgentPostsIntoSession` for `POST /sessions/{id}/files`, `POST /sessions/{id}/actions` and `POST /sessions/{id}/images` only: the owner as on `routePrincipalOwnsSession`, or the session's own agent with its session posting token, for that session and no other (404 for another). A handler that narrows reads `principalRestrictingRequest` and nowhere else — it returns nothing for the internal service and for an administrator, so an administrator can never be narrowed to the sessions carrying their own id. `principalIdentityOfRequest` is the one that names an administrator.

## Demo login and the two identity-carrying store proxies

**Login sessions** (`internal/server/login_sessions.go`, tables `login_sessions` and `login_attempts`). Every sign-in creates a row and sets the `llm_bridge_principal_session` cookie to a random 32-byte token; the row keeps only its SHA-256, the principal, the method (`demo` or `entra`), the identity binding for Entra, 12h expiry, last seen (written at most once a minute), and who revoked it and why. A cookie that names no row is 401 `login_session_unknown`, a revoked one `login_session_revoked`, an expired one `login_session_expired`. `POST /auth/logout` revokes on the server, so a copied cookie dies too; `GET /auth/sessions` and `POST /auth/sessions/{id}/revoke {"reason"}` let a person end their other sessions and an administrator end anyone's. The signed HMAC cookie this replaced on 2026-10-19 names no row, so its holders sign in again. Each session has a CSRF token, returned by the login response and `GET /auth/principal` and kept as it is (not hashed) so a reloaded page can get it back; `cmd/bridge-agent` reads it from its demo login and sends it. ⚠️ **Demo login is a stand-in, not a login.** Anyone who can reach `POST /auth/demo-login` can sign in as any active human principal by naming its id — there is no password — so never publish that route beyond a network you control. `LLMBRIDGE_DEMO_LOGIN_ENABLED` (default `true`, which this host relies on) set `false` makes it 404 `demo_login_disabled`. It checks the principal with principal-store: unknown → 400 `unknown_principal`, a group → 400 `principal_not_human`, disabled → 400 `principal_disabled`, unreachable → 502 `principal_store_unavailable`. **Entra ID sign-in** (`internal/server/entra_sign_in.go`, go-oidc and x/oauth2) is on when `LLMBRIDGE_ENTRA_TENANT_ID`, `_CLIENT_ID`, `_CLIENT_SECRET` and `_REDIRECT_URL` are all set (some but not all refuses startup; `_AUTHORITY_URL` exists for tests). `GET /auth/entra/start?return_to=/path` records an attempt (state and nonce hashed, PKCE verifier, 10 minutes, a browser-binding cookie so the callback must come from the same browser) and redirects to Entra; the provider's discovery document is read on first use, not at start. `GET /auth/entra/callback` consumes the attempt once (a replay is 400 `login_attempt_already_used`), redeems the code, verifies the ID token (signature against the JWKS, issuer exactly `<authority>/<tenant>/v2.0`, audience, exp, iat/nbf within 2 minutes, nonce, `tid` equal to the configured tenant) and resolves **`tid` + `oid`, never `sub` or an email**, through principal-store's `GET /identity-bindings/resolve`. A token failing a check is 401; an unprovisioned identity, a disabled principal or a non-human one goes back to `return_to?login_error=<code>`. Every attempt that reaches the callback ends with an `outcome` on its row; `GET /auth/login-attempts?outcome=identity_not_provisioned` (operator) shows the `tid`/`oid` to link. The login path never creates a principal or a binding. **Identity bindings** are administered through `GET`/`POST /admin/identity-bindings` and `POST /admin/identity-bindings/{id}/unlink` (operator routes, `internal/server/identity_binding_administration.go`), passed to principal-store with its status and body unchanged; the bridge sets `linked_by`/`unlinked_by` to the caller and refuses a body that names either, and a successful unlink revokes every live login session of that binding. `/kanban/<rest>` forwards to kanban-store `/api/<rest>`, `/grant-store/<rest>` to grant-store `/<rest>` and `/mailstack/<rest>` to mailstack `/<rest>`, all through one function, `serveStoreProxyAsPrincipal` in `internal/server/principal_identity_store_proxy.go`. mailstack alone also takes a bearer: the proxy presents `LLMBRIDGE_MAILSTACK_TOKEN` (503 `mailstack_proxy_not_configured` when unset) after deleting the client's, and mailstack narrows every request to the person's mail grants and tickets. Each requires a cookie or a session agent token (401 otherwise, and nothing is forwarded), **deletes** the client's `X-Principal-Id`, `X-Kanban-Store-Service-Token`, `X-Grant-Store-Service-Token`, `X-LLM-Bridge-Service-Token`, `X-LLM-Bridge-Peer-Token`, `Authorization` and the login cookie, and sets `X-Principal-Id` from the verified credential. The service token with no principal is 403 `store_proxy_requires_a_principal`; a store that cannot answer is 502. ⚠️ **kanban-store trusts `X-Principal-Id`, so users must reach it only through this proxy.**

## Peers: other llm-bridge-servers

Another llm-bridge-server can be given access to this one, and this one to it, each direction on its own (`internal/server/peers.go`, `internal/store/peers.go`; design note `d107154a-49ac-471b-a1b7-fc7975de37f3`). **What a peer may do is a principal's**: an administrator creates a principal of kind `peer` in principal-store and gives it grants, a group (a role), or `is_administrator` (everything, operator routes included). principal-store marks a peer `restricted_to_its_grants`, so unlike a human it is refused by a relation it holds no grant of — a link nobody granted anything gives nothing. **Issuing end**: `POST /peer-invites {"peer_principal_id","expires_in_seconds"?}` (operator; default an hour, at most a week) answers the one-time passphrase once and keeps its SHA-256; the other server redeems it at `POST /peer/redeem` (open; the passphrase is the credential; 401 unknown, 409 used, 410 expired) for a token kept here only as a hash in `peer_tokens`. `GET /peer-tokens`, `POST /peer-tokens/{id}/revoke {"reason"}`. **Calling end**: `POST /peer-links {"base_url","passphrase","display_name"}` (operator) redeems on the other server, keeps the token in auth-store (provider `llm-bridge-peer`, `base_url`, account the remote principal id) and records `peer_links`; `POST /peer-links/{id}/check` asks the other server's `GET /peer/self` who the token acts as there; `POST /peer-links/{id}/remove {"reason"}` deletes the credential (the token still works there until its operator revokes it, and the answer says so). ⚠️ **Invites and redemption are 409 `demo_login_enabled` while demo login is on**: a server that takes peers is reachable from another machine, and demo login signs anyone in as anyone. ⚠️ **A link's URL must be `https`**, verified with the system's roots; there is no switch to skip either. Every change records the administrator who made it, so the service token alone is 403 `peer_change_requires_a_principal`. Not built yet: the calling end's UI and its proxy for listing and running sessions on a linked server, and a peer naming which of its own users is asking.

## Session agent tokens

A session started as a principal gives its harness child `LLM_BRIDGE_GATEWAY_URL` and `LLM_BRIDGE_PRINCIPAL_TOKEN` (`internal/server/session_agent_token.go`). An MCP server or a shell command the agent runs sends the token as `Authorization: Bearer <token>` to the identity-carrying store proxies, and the request reaches the store as the session's principal exactly as a login cookie would. **The token is accepted nowhere else**: an `Authorization` header on any other route is 401 `authorization_header_not_accepted`. It is signed with the demo login signing key under its own domain separator, so it can never verify as a session posting token; the login cookie is not signed at all. Every request presenting it is checked against the store — the session must still exist, still belong to that principal and not be in a terminal state — which is how a token dies with its session. It lasts 24 hours and is minted at every spawn and resume, so a session that runs longer without being respawned loses gateway access until it is. This binds only agents that go through the gateway: in deployment kanban-store and grant-store must not be reachable from agent processes, and no store service token may sit in an agent's environment.

**Session files, and the session posting token.** `POST /sessions/{id}/files?filename=…` (body the bytes, `Content-Type` what they are) shares a file into a session, from the user or from its agent (`internal/server/session_files.go`). file-store keeps the bytes (`LLMBRIDGE_FILE_STORE_URL`, `FILE_STORE_SERVICE_TOKEN`; unset URL answers 503), table `session_files` keeps which session a file belongs to, a copy goes to `<LLMBRIDGE_SESSION_FILES_DIR>/<session>/<file id>/<filename>` for the agent to read, and a `session_file` event puts it in the conversation. `GET …/files` lists them and `GET …/files/{file_id}/content` relays file-store's answer with its headers unchanged. **Every local or runner harness child** (a runner child through `RunnerSpawn.Env`, since 2026-10-14; ssh has no way to deliver them), principal or not, gets `LLM_BRIDGE_SESSION_POSTING_TOKEN`, `LLM_BRIDGE_SESSION_ACTIONS_URL` and, when file-store is wired, `LLM_BRIDGE_SESSION_FILES_URL` (`session_posting_token.go`; until 2026-09-28 the session file token, `LLM_BRIDGE_SESSION_FILE_TOKEN`): and, with file-store, `LLM_BRIDGE_SESSION_IMAGES_URL`: a token that names only its session, carries no expiry, and is accepted only on the share, offer and image routes — not the session agent token, which is minted only for a principal, and no session here has one (0 of 1,098 in the week to 2026-09-27). `deploy.sh` installs `scripts/bridge-share-file` to `~/bin`, which is what an agent runs. **Session actions** (`internal/server/session_actions.go`) are buttons an agent puts in its chat with `bridge-button` (installed to `~/bin` by `deploy.sh`), which the server runs when the person confirms one. The agent offers one of `msg.OfferableSessionActionTypes` — `deploy` (a repo-store id; runs `bash -l -c ./deploy.sh` in the repo's path, through deploy-gate, with `LLM_BRIDGE_SESSION_ID` and `AI_AGENT` naming the button in the ledger), `run_scheduler_job` (a scheduler job id), `run_command`, `model_call`, `background_agent`, `fork_and_send` and `new_session_and_send` (a message), and `send_to_session` (`target_session_id` and a message) and `stop_session` (`target_session_id`), which act on another session for an agent that manages others, such as producer's orchestrator (`internal/server/session_action_targets.go`; `bridge-button --send-to <id> "<message>"` / `--stop-session <id>`); `sessionActionFieldsByType` says which offer fields each needs and allows. **A target session** must exist (404 `unknown_target_session`), must not be the offering session (400 `target_is_this_session`), must have the offering session's principal unless principal-store says that principal is an administrator, as the routes let an administrator reach any session (otherwise the same 404), and for a send must not be a harness subagent (409 `target_not_bridge_controlled`); it is checked at offer and again at confirm. `command` shows its id and display name, and since the renamer may change the name after the offer, a changed `command` does not refuse these two types (409 `session_action_changed`) the way it refuses the rest: the id is what runs. A send goes through `POST /sessions/{id}/send` (`serveInternally`) and a stop through `stopSession`, the function `POST /sessions/{id}/stop` calls; `result_session_id` is the target, and the output says what was done and the target's state read back after it. **`run_command`** (`internal/server/session_action_kinds.go`) runs the agent's `shell_command` with `bash -l -c` in `working_directory` or the session's own (`harness.WorkingDirForSession`), 30-minute limit, output as text or markdown; **a reviewer model reads it at offer** (`session_actions.review_model_role`, a stored setting, default the `balanced` role, called through the one-shot router) and its verdict — approve, caution or reject, with reasons — is stored on the action and drawn on the button; a rejected command is 409 `session_action_rejected_by_review` on run, and a reviewer that cannot be asked refuses the offer (502 `review_failed`), since a command shown with no review would look reviewed. **`model_call`** asks one model (`model` required: a role, which falls back down its list, or a model id or alias) with no tools; its `maximum_cost_usd` becomes an output-token limit at model-store list price on the dearest model the call may reach, a model with no price is refused, and the spend is recorded as `cost_usd` at the price of the model that answered. **`background_agent`** creates a session like `new_session_and_send` but with purpose `session-action`, the offer's cap as its spend ceiling and optionally its `model`, records `result_session_id` as soon as the session exists, and waits up to an hour for its `result` event, which becomes the output. All model use goes through `Server.sessionActionModels`, the server itself except in tests. **A `send_to_session` button can carry text boxes too**: its message names each as `$BRIDGE_INPUT_<NAME>` or `${BRIDGE_INPUT_<NAME>}`, every box must be named and no other, the typed value takes that place in the message sent, and no such box may be secret, since its value lands in the target's conversation. **A `run_command` button can carry text boxes** (`offer.inputs`, `internal/server/session_action_inputs.go`; `bridge-button --input NAME "Label"` / `--secret-input`): the confirm sends `{"inputs": {NAME: value}}`, each must be filled (400 `invalid_session_action_inputs`, with the action left offered), and the command gets them only as `$BRIDGE_INPUT_<NAME>`, so the reviewer, `command` and the log see the variable names, never the values; the values are stored in no row, event or log, and a secret one is blanked wherever it appears in the output or error. Table `session_actions.inputs` keeps only the declarations. `send_message` is refused since 2026-09-28 with a pointer to AskUserQuestion: every one offered until then was an answer choice, which only repeated the question the chat already draws; its old records still read and run. The agent writes the action's id in its reply and the chat draws the button there: the server writes `command`, the plain statement of what a confirm runs, and the chat shows it under the button. `POST …/actions/{action_id}/run` is `routePrincipalOwnsSession`, so the agent's token cannot confirm its own button; it describes the action again and answers 409 `session_action_changed` if what it would run is no longer what was shown, and an action runs once (409 `session_action_already_run`). Send, fork and create go through this server's own routes (`serveInternally`), so they behave as when a person calls them. Table `session_actions` is the log of each press — who confirmed it, when, the output and how it ended — and each change is also a `session_action` event carrying the whole record. An action still running when the server stops is settled `outcome_unknown` at the next start. `LLMBRIDGE_REPO_STORE_URL` and `LLMBRIDGE_SCHEDULER_URL` come from the `session-actions.conf` drop-in `deploy.sh` writes from those services' own units; either empty refuses its action type. A deploy action runs as a child of this server, so restarting the server kills a deploy in flight, and **when a run ends the server sends the session that offered it a report** (`session_action_report.go`: label, outcome, output after secret inputs are blanked, error), which starts the agent's next turn; a deploy is left to deploy-gate's own report, and an action settled `outcome_unknown` at start is reported too. **Images** (`internal/server/image_generation.go`): `POST /sessions/{id}/images {"prompt","reference_image_paths"}` runs the harness of the instance `image_generation.instance_id` names (stored setting, default `inst-codex-local`; empty switches images off, 503 `image_generation_off`) in `-generate-image` mode — llm-bridge-codex makes them on the Codex login, so no API key is spent — and shares each image into the session through `shareFileIntoSession`, the same path as a shared file; `POST /images` (operator) makes them and only answers with the paths. A harness's own `{"error"}` is passed on as 502 `image_generation_failed`. `deploy.sh` installs `scripts/bridge-image` and `cmd/bridge-mcp` to `~/bin`: **bridge-mcp is an MCP server over stdio that gives the same routes as tools** — `generate_image` (and a preview of each image at most 1024px, so the model sees what it made), `share_file` and `offer_button` (the offer record passed through unchanged) — reading the posting token and URLs from the environment Claude Code passes it (measured 2026-10-20: a stdio MCP server inherits the session's environment, so its tool-store row needs no `env`). Images a tool returned are served from log-store by `GET /sessions/{id}/entries/{eventId}/images/{index}`, proxied like the other entry routes.

## Which tools a session is offered

`injectMCPConfig` (`internal/server/tool_provision.go`) gives a session the MCP servers it is entitled to and rewrites `HarnessConfig` so `mcp_config` holds the path of the generated config file. An `mcp_config` the caller already set wins outright. Otherwise, in precedence order: (1) a `tool_store_tools` key on `HarnessConfig`, a JSON array of tool names the caller asked for by hand — removed afterwards, since it is an instruction and not state to ship, and an empty array is an honoured opt-out; (2) for a session with a `bundle_id`, exactly the tools bundle-store resolves the bundle to, narrowed by the principal's `can_use` grants when it holds any — **a bundle naming no tools provisions nothing and does not fall through**, because the caller chose a bundle and its answer was "no MCP servers"; (3) for a session with a principal, the tools its effective `can_use` grants name **that the session's instance has also opted in** in tool-store — a grant says who may have it, an opt-in says where it is wired; (4) the instance's tool-store opt-ins, the rows the bridge Tools page writes. **The two kinds of source fail differently on purpose.** A per-session request — a hand-named list or a bundle — that cannot be provisioned aborts the spawn, and so does a grant-store that will not answer. An instance's opt-ins are a standing preference, so a tool-store that is down logs loudly and the session starts with no MCP servers: a registry outage must not stop the fleet from working. Skills in a bundle's resolution are logged, not provisioned — Claude Code has no per-session skill set. `resolveToolOffer` returns the offer and its source; `injectMCPConfig` provisions what it returns. **A session on a runner machine gets the config's JSON, not a path** (`inlineMCPConfigForRunner`, `internal/server/computer_use.go`): a path names a file on this host, and Claude Code on the runner stopped with "MCP config file not found". **Computer use** is `harness_config.computer_use: true`, and `injectComputerUse` adds the runner's computer-use server (`msg.ComputerUseMCPServerName`, `llm-bridge-computer-use`; never `computer-use`, which Claude Code reserves and silently drops) only for Claude Code, on a runner machine whose owner switched it on (`PUT /machines/{id}/computer-use {"allowed": true}`, harness-store `machines.computer_use_allowed`, off by default), whose runner is connected and reported the tool in its Hello; otherwise the spawn is refused naming which of those failed. The runner installs and updates the tool itself (WSL: the Windows build under `%LOCALAPPDATA%\llm-bridge`) and is told, through `RunnerSpawn.ComputerUse`, to refresh it before such a session starts.

**Built-in harness tools, and paths a session may not read** (`internal/server/harness_tool_denials.go`). tool-store registers each harness's own tools as kind `harness` (`claude_code.Read`, `codex.shell_tool`…), on by default. At create, `snapshotSessionDefaultsIntoSession` pins `harness_config.disabled_tools` as the creator's list (or the harness default) **unioned** with the harness tools the session's bundle denies (bundle-store's `denied_tools`; a deny anywhere in the resolved set wins) and those tool-store has disabled, its master switch. The parts are pinned in `disabled_tools_by_layer`, and `POST /sessions/{id}/config` replaces only the creator's part, so no caller can give back a denied tool. A harness tool a bundle includes is never sent to `/provision`: the harness already has it. A bundle's `denied_read_paths` are pinned in `harness_config.denied_read_paths` and become Claude Code `Read(...)` deny rules in the synthesized `--settings`, an absolute path written `//path` because Claude Code reads `/path` as relative to the settings file and silently matches nothing (measured on 2.1.280; the rule holds under `bypassPermissions` and also hides the path from Glob and Grep). Create is refused (422) when the paths are denied on a harness other than claude_code, or while any tool tool-store tags `runs-commands` is still on, since a command reads around a Read rule; the spawn fails when a caller set `settings` itself on such a session. Every read of tool-store here fails the create rather than guessing: a master switch that cannot be read is not known to be off. Building the hook settings now fails the spawn too, instead of starting it without the permission gate.

**The tools a harness reports are sent to tool-store** (`internal/server/harness_tool_reports.go`). When a harness reports its session info (Claude Code's init), `onSessionInfo`, registered on the harness manager with `SetSessionInfoObserver`, posts the built-in tool names (not `mcp__…`) to tool-store's `POST /harness-tools/observed`. tool-store records when each was last seen and registers a name it has never seen switched off and tagged `unreviewed`, so every later session gets it in `disabled_tools` until a person reviews it. The session that first reports a new tool already has it. The post runs after the session has started, so a failure is logged as `[harness-tools] ERROR` rather than stopping anything.

## Operations: asynchronous work with a receipt

`POST /operations` accepts a `msg.OperationIntent` and answers with a `msg.OperationReceipt`; llm-bridge's `docs/OPERATIONS.md` is the contract (states, idempotency, correlation headers, redaction). `internal/operations` is the coordinator, `internal/operationstore` its SQLite file (`LLMBRIDGE_OPERATIONS_DB`, apart from the session database), `internal/executors` one executor per operation type, and `internal/server/operations.go` the routes. **Every receipt change goes through `operationstore.Update` and writes one event whose sequence is the new revision** — never write a receipt another way, or the SSE stream and `Last-Event-ID` resume stop matching the record. Workers claim under a lease (`operations.lease_duration`, renewed at a third of it); releasing a lease retires its token, so a worker that lost it gets `ErrLeaseLost` on its next write and must return. An effect recorded with `RecordEffect` and never settled makes the operation `unknown` whatever the executor reports, and reconciliation never runs it again. At start, and every half lease, operations left running by another process or an expired lease go to the executor's `Reconcile`. `classification.run` is `executors.ModelClassifier`: items in batches of 20, one one-shot call per batch with a schema that allows only the taxonomy's values, and each answer held to the taxonomy again afterwards (an invented value is dropped, and an empty required axis or a missing answer sets `needs_review`). **The taxonomy varies by board**: it comes inline or from the kanban-store board named in `taxonomy_board_id`, read as the operation's principal from kanban-store's `GET /api/boards/{id}/classification` (`kanbanclient.BoardTaxonomy` sends `X-Principal-Id` without the service token, because kanban-store lets the token win), and the result records the taxonomy and the board's `taxonomy_revision`. The model is shown only `Selectable()`: archived axes and values stay in the board's taxonomy for history and are never offered. `llm.completion` (`executors.LLMCompletion`) is one routed call — the server itself is the `OneShotCaller`, so no executor calls a provider. **Both model executors go through the one-shot router**: `Server.OneShotRoute` resolves the input's `model` (or `operations.completion_model_role`, empty by default, so an input must name one) — a role becomes its whole list, a model id or alias that model alone — and an unknown model or role, or none, fails before any call. Under a budget, a model with no list price is skipped for the next, and a call every model of which was skipped for price fails `model_price_unknown`.

**The one-shot router: a role in, the first model that answers out** (`internal/oneshotrouting`, wired in `internal/server/oneshot_routing.go`). Every background model call names a model-store role and a `Caller` — `signal-classifier` (`signal_classifier.model_role`, default `balanced`; on this host `turn-end-signal`, the role eval-store eval_run_000010 chose), `question-triage` (`question_triage.model_role`, `balanced`), `prompt-drift-tagger` (`prompt_drift_tagger.model_role`, `balanced`), `session-renamer` (`session_renamer.model_role`, `efficient`), `session-actions-review` (`session_actions.review_model_role`, `balanced`), the two operation executors — and so does `POST /oneshot` (operator route; body `msg.OneShotRequest` with `model_role` and `caller`, never `model`: 400 `model_not_accepted`, `no_model_role`, `unknown_model_role`, `prompt_required` or `invalid_body`; 503 when model-store has no models for the role; 502 `all_models_failed` with `attempts`; 200 a `msg.OneShotResponse` with `model`, `instance_id` and `attempts`). `POST /instances/{id}/oneshot` still takes a model and an instance, unrouted. model-store keeps each role's models in order (`RoleModels`); for each, the router takes the instance `oneshot.instance_by_provider` names for its provider (`anthropic:inst-cc-local,openai:inst-codex-local`; a provider with none is a failed attempt, not a guess), skips it when usage-store (`LLMBRIDGE_USAGE_STORE_URL`, `GET /api/usage/limits`, read at most every 30s) reports a fresh window at 100% for the subscription that instance's harness bills (`UsageProviderByHarness`: `claude_code`→`anthropic`, `codex`→`codex`; any other harness is never skipped; a usage-store that cannot be read is logged and skips nothing), and otherwise calls it. A failure is logged as `[oneshot] role=… caller=… model X failed: …; trying Y` and the next model is tried. The harness is sent the model id, never the role. Both `llm-bridge-claudecode` and `llm-bridge-codex` implement `-oneshot`. The renamer is one such call since 2026-09-30: before, it started a whole Claude Code session on the target's instance with no model, which curled its title back to `POST /sessions/{id}/auto-rename` (removed); a slot a title call holds is known only to the process making it, so a restart frees it. `organization_id` is a principal-store group the caller must belong to unless it is an administrator or the service token. `checkOperationGrant` reads grant-store's `can_run_operation` on `operation_type`, lenient or strict by `operations.grant_enforcement`; grant-store checks an `operation_type` id against `GET /operation-types`, which is why that route is open. **Budgets are list-price dollars** (`ModelListPrice` from model-store; cache tokens at the input price): an organization's monthly limit (`/operation-budgets`, operator routes, UTC months) and the root intent's `maximum_cost_usd`, the lower winning. An executor calls `SpendingAllowance` before each model call and `RecordModelCall` after, which writes the receipt's usage and the `operation_spend` ledger in one transaction. Not built yet: capabilities, retention.

## The grant gate: can_dispatch_on and can_run_as

`checkPrincipalMayRunHere` (`internal/server/grant_gate.go`) is where grant-store's `can_dispatch_on` and `can_run_as` are enforced: a session started as a principal may start only on an instance, or an instance of a machine, that the principal's grants name, and only as an agent they name. **What a grant allows is decided in one place, `principal_grants.go`** (`grantedResourcesOf`, `dispatchGrantsOf`), which the gate, the tool offer, `checkOperationGrant`, the instance list and the effective-config view all read: a grant of `*` names every resource of its type; **lenient by the operator's choice**, a principal holding no grant of a relation is not restricted by it, so a default principal set before any grant exists locks nothing out — **unless principal-store marks its kind `restricted_to_its_grants`**, as it does a peer, which holding none refuses; a principal holding any grant of a relation is refused outside it. `operations.grant_enforcement=strict` makes every principal restricted to its grants for `can_run_operation`. A grant-store that cannot answer is an error — a session that named a principal must not start because the check failed. The gate runs twice on purpose: at `POST /sessions`, so the caller gets the refusal with its reason, and again at spawn, so a session created before its principal's grants changed is judged against the grants as they are now. `grantGateStatus` maps the failure: `ErrNotGranted` → 403 `not_granted`, naming what the grants do allow; an unknown principal → 400 `unknown_principal`; anything else → 502 `grant_store_unavailable`. A session's `agent_id` is agent-store's slug today while a grant names its numeric id, so the slug is resolved through the in-process agent-store; a slug that will not resolve is a refusal, not a pass. Skills are not enforced: a `can_use` grant on a skill is stored and nothing reads it.

## The host prompt every harness receives

At start `syncPromptHarnessDeliveries` (`internal/server/prompt_context.go`) records a `prompt_harness_deliveries` row for every harness in `msg.AllHarnesses` that has none, and touches no row that already exists: agent-store refuses to resolve a prompt for a harness with no row, so a harness added to `msg.AllHarnesses` gets one on the next start. `harnessesThatReadTheirOwnPromptFile` is only the seed — `claude_code` and `jig` read `CLAUDE.md` themselves (jig launches the `claude` binary), everything else is injected — and **the row is the truth after that**, edited on the Files page. `injectPromptContext` puts the host prompt, the prompt of every project collection the session's working directory sits in, and the **context sections its card's tags select** into `HarnessConfig`; agent-store decides what that is per harness, giving a harness that reads a rendered file only the collections that file does not already carry, so no harness gets the same text twice and none gets less than the others. The working directory is the spawn's own (`harness.WorkingDirForSession`: session, then instance, then machine) — until 2026-09-21 this read it from `DisplayName`, so an injected harness whose directory came from those fields got no repo prompt. **The key follows the delivery row**: an `inject` harness gets `system_prompt`, a `native_file` harness gets `append_system_prompt` — Claude Code maps `system_prompt` to `--system-prompt`, which replaces its default prompt. A caller that set `system_prompt`, or the key this would write, wins. A session's `card_id` (checked with kanban-store at create: 400 `unknown_card`, 502 `kanban_store_unavailable`; carried to forks and subagents) is read for its tags at **every** spawn (`kanbanclient.CardTags`), so a tag added to a card reaches the next spawn; a card that cannot be read logs an ERROR and the session starts without its context, like a failed prompt resolution. jig reads neither key — it takes its prompt from its YAML profile — so jig sessions get no injected text. The mutation is in memory and not persisted, so an edit to the prompt takes effect on the next spawn. A held prompt drift that adds sections gets its tags from one routed call on `prompt_drift_tagger.model_role` (`prompt_drift_tagger.go`); it **proposes tags only** — a section's title is its heading — and an empty role turns labelling off, leaving drifts detected and held, unlabelled.

## The effective-config view

`GET /sessions/{id}/effective-config` answers for a stored session and `GET /effective-config?harness=…&instance_id=…&principal_id=…&agent_id=…&bundle_id=…&board_id=…&card_id=…&tag=…` for one that does not exist yet (`internal/server/effective_config.go`). Both return `msg.EffectiveConfig`: eleven settings — model, effort, max_budget, disabled_tools, permission_mode, principal, instance, agent, bundle, tools, context — each with the layer that decided it, the record it is stored in and one sentence of detail, plus `warnings` naming what would refuse a spawn. The eleven layers, narrowest first, are `session`, `request`, `tag_rule`, `board`, `bundle`, `grant`, `instance`, `harness_default`, `global`, `registry` and `none`, and the legend travels in the answer. **It reports and decides nothing** and it reads the spawn's own code (`resolveToolOffer`, `resolveModelSelection`, the grant gate's reads), so the view cannot say one thing while the spawn does another; keep it reading that code rather than re-deriving a setting here. A dry run with `board_id` reads kanban-store's effective defaults through `kanbanclient.EffectiveDefaults` — needs `LLMBRIDGE_KANBAN_STORE_URL`, else 503 `kanban_store_not_configured`, and 502 `kanban_store_unavailable` when the store will not answer — and fills in whichever of principal, agent, instance and bundle the caller left empty, exactly as the dispatcher would, attributing each to `board` or `tag_rule`. A principal still empty is then filled from `bridge-prefs.default_principal_id`, as the chat pane does, and the answer says so. **Model, effort, spend ceiling and disabled tools are decided once, at `POST /sessions`, by one precedence: the session's own value, then its bundle, then the per-harness default in bridge-prefs** (and for the model only, model-store's `default` role as the floor). `snapshotSessionDefaultsIntoSession` (`internal/server/session_defaults.go`) resolves the bundle once, pins each winner into the row, and records the layer that decided it — the model's in `harness_config.model_selection` (`selected_by` is `session`, `bundle`, `prefs` or `role`), the other three in `harness_config.setting_layers` — so a later change to a bundle or to the harness defaults does not move a session that exists, and the view reads the record instead of guessing. A bundle names a model and an effort and nothing else. A sent `max_budget: 0` and a sent empty `disabled_tools` are the creator's answers and outrank a default; an absent one takes it. `POST /sessions/{id}/config` relabels what it changes as the session's own. A bundle that cannot be resolved refuses the create (422 `model_unresolvable`), as the spawn would have. Until 2026-09-18 only the chat pane applied the harness defaults, by copying them into its own request, and nothing applied a bundle's model or effort — so a dispatched session ran with no ceiling at the harness's own effort whatever its board's bundle said. The chat pane still sends what its controls show, which reads as the session's own. A dry run pins what create would for a creator who names none of the four, which is what a dispatcher sends.

## GET /hook-options

`GET /hook-options` serves what a hook editor must not hardcode: the harnesses the spawn actually wires hooks into, read from `hookConfigKeyByHarness` — `claude_code` under `settings`, `codex` under `codex_hooks`, held to `injectHookSettings` by a test — each with its known events from `harnessHookEvents` and the help text for its matcher syntax, and the scope kinds narrowest first (`session`, `instance`, `global`). `harnessHookEvents` is the same map `GET /harnesses` already serves as `hook_events`, so there is one list and not two; add a harness's events there and both routes follow. bridge-ui's `/hooks` page is the consumer, and it marks a hook stored for a harness this answer does not name as one that never runs.

## The service inventory

`GET /services` joins healthcheck's status (`LLMBRIDGE_HEALTHCHECK_URL`) to each service's processes and the SQLite files they hold open. Processes are found in `/proc` — a systemd check by the cgroup its processes sit in, an HTTP check by the process listening on the URL's port — and **never through DBus**, which the unit has no session for. `GET /services/databases/schema` and `GET /services/databases/rows` open one such file with `mode=ro` and `query_only`, so nothing on this path can write, and **only a file some watched service holds open right now can be read**; anything else is 404. A column whose name looks like a credential comes back masked (`internal/serviceinventory/mask.go`): the name is split on `_`, `-`, `.` and camelCase boundaries and each word matched against a list, so `api_key`, `apiKey`, `refresh_token`, `client_secret`, `password_hash` and `runner_token_hash` are masked while `max_tokens`, `input_tokens`, `keyword` and `session_key` are not. **Bare `key` is deliberately not enough** — across every live database on this host it names a lookup key far more often than a secret — so it masks only beside a qualifier: api, access, private, secret, signing, ssh. All three routes are operator-only.

## Session states, their reasons, and how a session ends

The state of a session is derived in one place, `internal/harness/derivation.go`, and written to the row only with its whole `msg.SessionStatus` (`store.WriteSessionStatus`). **Every status carries `reason`**, from the one list `msg.SessionStateReasons` (llm-bridge `msg/session_state_reason.go`), which `GET /session-taxonomy` serves as `state_reasons`; a spawn that fails also carries `reason_detail`, the error itself. A reason not on that list is a bug here. The server forces a state only through `ForceSessionState` / `ForceSessionStateWithDetail`, which write the reason whether or not the process still has a derivation, and which take the derivation's `publishMu`: deciding a status and writing it are one step, so a stop cannot land between a turn's batch being built and being written (until 2026-10-19 the batch's idle won, br_1792020662192496685). A state the server forced to `completed`, `aborted` or `error` holds against the dying process's late frames, a runner's included; only a new turn (`user_message`) or a lifecycle state the server sends moves it. **The idle reaper's kill is unchanged** — 15 minutes quiet (60 in terminal mode), never a session the harness reports busy, about 150MB freed per process, and a cascade of them took the host down on 2026-05-29 — but `Manager.ReapIdleProcess` records what it found, reason `idle_reaped`: `idle` becomes `completed`, `completed` stays, `awaiting_user` and `awaiting_permission` stay (the answer restarts the session), `error` stays, and anything else becomes `aborted` as before. Until 2026-10-19 every reap read `aborted`, so 903 autoworkers that had finished read as stopped. **A harness subagent** (`controlled_by: harness`, which every gate on resume, send and buttons reads) runs inside its parent's process, so it ends by its parent's task status — completed → `completed`, failed → `error`, cancelled → `aborted`, reasons `task_*` — or, when that process is gone first, `error` with `parent_process_exited`, written by the router, the watchdog or the startup reconcile. The watchdog leaves a subagent alone while its parent's process runs. Every subagent row with a parent gets `controlled_by: harness` at start (an idempotent migration) and from discovery when it links one. `ArchiveOld` spares every state in `msg.ActiveSessionStates`, and wakeup redelivery after a restart skips a session that was `aborted`, `completed` or reaped.

# Access and operations

## Unit, listen address and required settings

The unit is a **system** unit, `/etc/systemd/system/llm-bridge.service` — not a user unit, so `systemctl --user cat llm-bridge.service` finds nothing. It runs as `kayushkincom` with `ExecStart=/usr/local/bin/llm-bridge`. Drop-ins live in `/etc/systemd/system/llm-bridge.service.d/`: `local.conf` is readable by root only, `oom.conf` sets the OOM policy, `principal-gating.conf` sets `LLMBRIDGE_PRINCIPAL_STORE_URL`, `LLMBRIDGE_KANBAN_STORE_URL` and `LLMBRIDGE_GRANT_STORE_URL` and loads `EnvironmentFile=~/.config/principal-gating-tokens.env`, and `file-store.conf`, which `deploy.sh` writes (and a rollback takes back), sets `LLMBRIDGE_FILE_STORE_URL` from `FILE_STORE_ADDR` in file-store's own unit and loads `EnvironmentFile=~/.config/file-store-tokens.env` — file-store's own file, mode 600, never the shared one. It listens on `LLMBRIDGE_LISTEN_ADDR`, `:8160` on every interface. Five settings are **required at startup** and a missing or too-short one is a startup error naming the variable: `LLMBRIDGE_DEMO_LOGIN_SIGNING_KEY` (at least 32 bytes), `LLMBRIDGE_SERVICE_TOKEN` (at least 32 bytes), `LLMBRIDGE_PRINCIPAL_STORE_URL`, `LLMBRIDGE_KANBAN_STORE_URL` and `LLMBRIDGE_GRANT_STORE_URL`. `config.ValidateRequestAuthorizationSettings` is the whole check and `main` refuses to start on it, while `server.New` panics on the two credentials alone — so no code path builds a server that gates nothing while looking gated. **Every environment variable this process reads is declared once**, in `internal/config/settings.go` (`SettingDefinitions`): key, variable, kind (`wiring`, `path`, `secret`, `behaviour`), type, default and what it changes. `config.Load` reads `Config` through that list with llm-bridge's `servicesettings` package and **stops the process** on a value that does not parse as its type and on a set `LLMBRIDGE_` variable nothing declares — both used to pass in silence, the first as the default and the second as a misspelling that did nothing. `TestEveryEnvironmentVariableTheServerReadsIsDeclared` holds every `os.Getenv` in the repo to the list, so add the declaration with the read. `GET /settings` (operator route) describes the server from it — each value in force and whether the environment, the stored record or the default decided it; a secret says only that it is set — and `PUT /settings/{key} {"value":…}` changes a **stored behaviour setting** with no restart: `signal_classifier.model_role`, `.timeout`, `.maximum_characters`, `.opt_out_harnesses`, `question_triage.model_role`, `prompt_drift_tagger.model_role`, `session_renamer.model_role`, `session.idle_timeout`, `session.pty_idle_timeout`, `external_activity.poll_interval`, `oneshot.instance_by_provider`, `operations.completion_model_role`, `operations.grant_enforcement`, `session_actions.review_model_role` and `image_generation.instance_id`. They live in table `service_settings` of the bridge database; the environment seeds each row once, the first start a key exists, and **the row is then the only source — setting the variable does nothing**, and the description says so in a note. A `model_role` setting is checked with model-store on write (400 for a name that is not a role or a role with no models, 502 when it cannot answer); `oneshot.instance_by_provider` is checked with model-store and harness-store. On 2026-09-30 the model and instance settings became roles: at start `MoveServiceSettingKeys` copies `operations.completion_instances` to `oneshot.instance_by_provider` and deletes the rows of `config.RetiredStoredSettingKeys`, so a setting that was renamed keeps its value and one that was replaced starts at its default. Read a stored setting at the time of use with `s.settings.String(config.Setting…)`, never from `s.cfg`: `Config` holds the value the process started with. Wiring, paths and secrets change only in the unit and its drop-ins (409 on a `PUT`). Defaults for addresses are in `internal/productiondefaults`.

## The server's own secrets never reach a child process

`config.SecretEnvironmentVariableNames` lists every variable that must never reach a process this server spawns, and `internal/childprocessenv` strips them from each harness child. A harness child runs an agent that can execute shell commands, so whatever is in its environment the agent can read: the demo login signing key would let it mint a session agent token for any principal, the service token would make it the unrestricted internal caller, a store service token would let it bypass that store's per-principal enforcement, and the Entra client secret would let it redeem a code meant for this server. The six are `LLMBRIDGE_DEMO_LOGIN_SIGNING_KEY`, `LLMBRIDGE_SERVICE_TOKEN`, `GRANT_STORE_SERVICE_TOKEN`, `KANBAN_STORE_SERVICE_TOKEN`, `FILE_STORE_SERVICE_TOKEN`, which reads every file file-store holds, and `LLMBRIDGE_ENTRA_CLIENT_SECRET`. `LLMBRIDGE_MAILSTACK_TOKEN` and `AUTH_STORE_TOKEN` are left out on purpose: the operator chose to keep them in agent environments. ⚠️ **The two store tokens carry the store's own name and have no `LLMBRIDGE_` prefix**: grant-store, kanban-store, dash and the scheduler all read them from one host-local file, `~/.config/principal-gating-tokens.env`, and this unit loads the same file. Reading them under `LLMBRIDGE_`-prefixed names failed twice over — the grant token read as empty, so grant-store answered every spawn-time read with 401, and the real variables were not on the strip list, so every harness child inherited both. The kanban name is taken from `internal/kanbanclient` rather than restated, so there is one spelling read in one place and stripped in another. A new secret goes in the constant block and in `SecretEnvironmentVariableNames` in the same change.

# Working in this repo

## Module, build and deploy

Module `github.com/kayushkin/llm-bridge-server`, Go 1.25, pushing to `github.com/kayushkin/llm-bridge-server`. It builds from plain main clones with **no `go.work`**, and the shared deploy gate refuses a build that reads a sibling tree on a side branch — so fix the sibling rather than adding a `GOWORK` file. Deploy only with `./deploy.sh` from the main clone on the default branch. It runs `~/bin/deploy-gate check` first, then hands itself to `deploy-gate detach`, which re-runs it in a transient systemd unit under `system.slice`: an agent deploying from inside a bridge session sits in the service's own cgroup, `sudo systemctl stop llm-bridge.service` would take the deploy down with it, and `setsid nohup` does not escape a cgroup kill. The detached run logs to `~/.cache/llm-bridge-deploy.log`, which is under `$HOME` because a transient unit gets a private `/tmp`. ⚠️ **The deploy stops and restarts the service, killing every live bridge session including the deploying agent's own** — background subagents die with it, so finish or wait for them first. **When the deploy ends, pass or fail, the unit sends its outcome and the log's last lines to the session that started it** (the bridge puts `LLM_BRIDGE_SESSION_ID` in every local harness child for this), and that message starts a new turn. So after `./deploy.sh` returns, end the turn and say the deploy is running; do not promise to check "once the session resumes". The bridge resumes a session only when a turn was cut off, and a turn that had ended before the restart used to sit idle for good (2026-09-09, 2026-09-22, 2026-09-26). A turn that ended waiting on a `ScheduleWakeup` is the exception: the restart kills the timer with the process, so `RedeliverWakeupsLostInRestart` (`internal/server/wakeup_redelivery.go`) sends its prompt at the time it was due, and the idle reaper holds a live session until its wakeup comes due. Do not start a second bridge restart in the same turn either. `startOnInstance` holds a lock per session, so the report, auto-resume and a user's message arriving together after a restart start one harness process, not two.

## Test sessions you start by hand

A test session you start by hand to check a change must not pass for a chat. The server stores the `type` and `origin` a caller sends and infers neither, and the chat lists every `type: interactive` session as a conversation with the user. So never copy the chat's own create request (`"type":"interactive","purpose":"chat","origin":"frontend"`) into a `POST /sessions` of your own. Send `"type":"autonomous"`, an `origin` that names your test, such as `agent-test`, and `manager_session_id` set to your own session's id, which is in `$LLM_BRIDGE_SESSION_ID`. That puts the test under your session in the session tree; the server refuses an id it has no session for (400 `unknown_manager_session`) and takes the root and depth from that session. `bridge-agent` does all three itself (`-manager-session` overrides the parent). On 2026-09-29 and 2026-09-30 two wakeup tests sent the chat's request, and both showed up in the chat as conversations the user had never started, with nothing pointing back to the session that made them.
