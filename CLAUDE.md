# About llm-bridge-server

## What it owns

`:8160`, listening on every interface. The central session server and HTTP gateway of the llm-bridge ecosystem: it manages harness lifecycle, streams session events over SSE, holds credential bindings, and runs agent-store, memory-store, harness-store, hook-store, snapshot-store and model-store as embedded libraries. agent-store is one of them, which makes this server **the path to the host prompt source** rather than standalone agent-store on `:8300`. It also serves the service inventory and the effective-config view, so it is the single backend behind bridge-ui's whole surface. README "Routes" is the route table, generated from `routeDescriptions` and `routeAccessRules`; README "Who may call what" is the reference for who may call what.

## Where this prompt lives

These sections are stored in agent-store as a project prompt collection and rendered, with identical text, to `AGENTS.md` and `CLAUDE.md` at the root of this repo, so that whichever file a harness reads it gets the same thing. Edit them on dash `/files`, or edit either rendered file: the 15-minute scan carries the edit back into the sections and out to the other file. The host prompt keeps one row for this repo with only what an agent elsewhere needs.

# How it works

## Request authorization: every route is classified

Every request passes through `authorizeAndServe` (`internal/server/request_authorization.go`) before the mux dispatches it, and there is no way to switch that off: `config.ValidateRequestAuthorizationSettings` makes the credentials mandatory at startup. Each route is classified in `routeAccessRules`, keyed by the exact pattern it is registered under. **A pattern with no rule is 403 `route_not_classified` to everyone but the service token**, so a route added later is closed until someone decides who may call it; `TestEveryRegisteredRouteIsClassified` fails when a `HandleFunc` or `Handle` in the package has no rule, so add the rule in the same change as the route. Add its one-line description to `routeDescriptions` (`route_descriptions.go`) too, and regenerate the README table with `go test ./internal/server -run TestReadmeRouteTable -update-readme-route-table`; a test fails until both are done. Callers, in precedence order: the internal service (`X-LLM-Bridge-Service-Token` equal to `LLMBRIDGE_SERVICE_TOKEN` — unrestricted, not even held to the route table, and a wrong token is 401 rather than a silent downgrade); the internal service acting as a person (the same token plus `X-Principal-Id`, which dash sends for one of its logged-in users, and which is **401 on its own** on every route); a principal (a valid login cookie, or a session agent token on the store proxies only); nobody (401 on anything that is not open or a harness callback). Whichever principal a request resolves to is read from principal-store first (`request_principal_lookup.go`): one it does not know is 400, a disabled one is 403, and one it marks `is_administrator` is past every per-resource check.

## The route classes and how a handler narrows its answer

`routeOpenToEveryone`: `GET /health` and the three `/auth/…` routes. `routeHarnessCallback`: the Claude Code and codex prehooks, the pty sidecar, `POST /hooks/exec/{id}`, `POST /sessions/{id}/auto-rename`, the runner routes and the seed proxies — processes this server spawned, or runners, none of which carry a login, so each handler keeps whatever check it makes and nothing more. `routeOperatorOnly`: the service token or an administrator, 403 `operator_route` otherwise. `routePrincipalCreatesSession` on `POST /sessions`, where **the session is created as the calling principal whatever the body says**. `routePrincipalOwnsSession` and `routePrincipalOwnsSignal`, where a principal reaching someone else's gets **404** — the same answer as a missing one. `routePrincipalSeesOwnSessionsOnly`, where the handler narrows the answer itself. `routePrincipalReadsCatalog` for the read-only catalogs a chat UI needs. `routePrincipalRefusedCannotBeFiltered` for `GET /sessions/search`, `GET /sessions/aggregates` and `GET /snapshots/blob/{sha}`: log-store answers them across every session and a blob is shared, so a principal is refused rather than shown other people's data. `routePrincipalOrSessionAgentThroughStoreProxy` for `/kanban/` and `/grant-store/`. A handler that narrows reads `principalRestrictingRequest` and nowhere else — it returns nothing for the internal service and for an administrator, so an administrator can never be narrowed to the sessions carrying their own id. `principalIdentityOfRequest` is the one that names an administrator.

## Demo login and the two identity-carrying store proxies

⚠️ **The login is a stand-in for a real login system, not one.** Anyone who can reach `POST /auth/demo-login` can sign in as any active human principal by naming its id — there is no password — so never publish that route beyond a network you control. It checks the principal with principal-store: unknown → 400 `unknown_principal`, a group → 400 `principal_not_human`, disabled → 400 `principal_disabled`, unreachable → 502 `principal_store_unavailable`. On success it sets the `llm_bridge_principal_session` cookie, holding the principal id and a 12h expiry signed with HMAC-SHA256. `GET /auth/principal` reads it back and `POST /auth/logout` clears it; the cookie is stateless, so a copy taken before logout stays valid until it expires. `/kanban/<rest>` forwards to kanban-store `/api/<rest>` and `/grant-store/<rest>` to grant-store `/<rest>`, both through one function, `serveStoreProxyAsPrincipal` in `internal/server/principal_identity_store_proxy.go`. Each requires a cookie or a session agent token (401 otherwise, and nothing is forwarded), **deletes** the client's `X-Principal-Id`, `X-Kanban-Store-Service-Token`, `X-Grant-Store-Service-Token`, `X-LLM-Bridge-Service-Token`, `Authorization` and the login cookie, and sets `X-Principal-Id` from the verified credential. The service token with no principal is 403 `store_proxy_requires_a_principal`; a store that cannot answer is 502. ⚠️ **kanban-store trusts `X-Principal-Id`, so users must reach it only through this proxy.**

## Session agent tokens

A session started as a principal gives its harness child `LLM_BRIDGE_GATEWAY_URL` and `LLM_BRIDGE_PRINCIPAL_TOKEN` (`internal/server/session_agent_token.go`). An MCP server or a shell command the agent runs sends the token as `Authorization: Bearer <token>` to the identity-carrying store proxies, and the request reaches the store as the session's principal exactly as a login cookie would. **The token is accepted nowhere else**: an `Authorization` header on any other route is 401 `authorization_header_not_accepted`. It is signed with the demo login signing key under its own domain separator, so it can never verify as a login cookie and a cookie can never verify as a token. Every request presenting it is checked against the store — the session must still exist, still belong to that principal and not be in a terminal state — which is how a token dies with its session. It lasts 24 hours and is minted at every spawn and resume, so a session that runs longer without being respawned loses gateway access until it is. This binds only agents that go through the gateway: in deployment kanban-store and grant-store must not be reachable from agent processes, and no store service token may sit in an agent's environment.

## Which tools a session is offered

`injectMCPConfig` (`internal/server/tool_provision.go`) gives a session the MCP servers it is entitled to and rewrites `HarnessConfig` so `mcp_config` holds the path of the generated config file. An `mcp_config` the caller already set wins outright. Otherwise, in precedence order: (1) a `tool_store_tools` key on `HarnessConfig`, a JSON array of tool names the caller asked for by hand — removed afterwards, since it is an instruction and not state to ship, and an empty array is an honoured opt-out; (2) for a session with a `bundle_id`, exactly the tools bundle-store resolves the bundle to, narrowed by the principal's `can_use` grants when it holds any — **a bundle naming no tools provisions nothing and does not fall through**, because the caller chose a bundle and its answer was "no MCP servers"; (3) for a session with a principal, the tools its effective `can_use` grants name **that the session's instance has also opted in** in tool-store — a grant says who may have it, an opt-in says where it is wired; (4) the instance's tool-store opt-ins, the rows the bridge Tools page writes. **The two kinds of source fail differently on purpose.** A per-session request — a hand-named list or a bundle — that cannot be provisioned aborts the spawn, and so does a grant-store that will not answer. An instance's opt-ins are a standing preference, so a tool-store that is down logs loudly and the session starts with no MCP servers: a registry outage must not stop the fleet from working. Skills in a bundle's resolution are logged, not provisioned — Claude Code has no per-session skill set. `resolveToolOffer` returns the offer and its source; `injectMCPConfig` provisions what it returns.

**Built-in harness tools, and paths a session may not read** (`internal/server/harness_tool_denials.go`). tool-store registers each harness's own tools as kind `harness` (`claude_code.Read`, `codex.shell_tool`…), on by default. At create, `snapshotSessionDefaultsIntoSession` pins `harness_config.disabled_tools` as the creator's list (or the harness default) **unioned** with the harness tools the session's bundle denies (bundle-store's `denied_tools`; a deny anywhere in the resolved set wins) and those tool-store has disabled, its master switch. The parts are pinned in `disabled_tools_by_layer`, and `POST /sessions/{id}/config` replaces only the creator's part, so no caller can give back a denied tool. A harness tool a bundle includes is never sent to `/provision`: the harness already has it. A bundle's `denied_read_paths` are pinned in `harness_config.denied_read_paths` and become Claude Code `Read(...)` deny rules in the synthesized `--settings`, an absolute path written `//path` because Claude Code reads `/path` as relative to the settings file and silently matches nothing (measured on 2.1.280; the rule holds under `bypassPermissions` and also hides the path from Glob and Grep). Create is refused (422) when the paths are denied on a harness other than claude_code, or while any tool tool-store tags `runs-commands` is still on, since a command reads around a Read rule; the spawn fails when a caller set `settings` itself on such a session. Every read of tool-store here fails the create rather than guessing: a master switch that cannot be read is not known to be off. Building the hook settings now fails the spawn too, instead of starting it without the permission gate.

## Operations: asynchronous work with a receipt

`POST /operations` accepts a `msg.OperationIntent` and answers with a `msg.OperationReceipt`; llm-bridge's `docs/OPERATIONS.md` is the contract (states, idempotency, correlation headers, redaction). `internal/operations` is the coordinator, `internal/operationstore` its SQLite file (`LLMBRIDGE_OPERATIONS_DB`, apart from the session database), `internal/executors` one executor per operation type, and `internal/server/operations.go` the routes. **Every receipt change goes through `operationstore.Update` and writes one event whose sequence is the new revision** — never write a receipt another way, or the SSE stream and `Last-Event-ID` resume stop matching the record. Workers claim under a lease (`operations.lease_duration`, renewed at a third of it); releasing a lease retires its token, so a worker that lost it gets `ErrLeaseLost` on its next write and must return. An effect recorded with `RecordEffect` and never settled makes the operation `unknown` whatever the executor reports, and reconciliation never runs it again. At start, and every half lease, operations left running by another process or an expired lease go to the executor's `Reconcile`. `classification.run` is `executors.ModelClassifier`: items in batches of 20, one one-shot call per batch with a schema that allows only the taxonomy's values, and each answer held to the taxonomy again afterwards (an invented value is dropped, and an empty required axis or a missing answer sets `needs_review`). **The taxonomy varies by board**: it comes inline or from the kanban-store board named in `taxonomy_board_id`, read as the operation's principal (`kanbanclient.BoardTaxonomy` sends `X-Principal-Id` without the service token, because kanban-store lets the token win), and the result records the taxonomy and the board's `updated_at`. `llm.completion` (`executors.LLMCompletion`) is one call through `runOneShot` — the server itself is the `OneShotCaller`, so no executor calls a provider. **Both model executors route by model**: `Server.CompletionTarget` resolves the input's `model` (or `operations.completion_model`) through model-store — an id, an alias or a role such as `efficient` — and sends the resolved id to the instance `operations.completion_instances` maps its provider to (`anthropic:inst-cc-local,openai:inst-codex-local`); an unknown model, no model, or an unmapped provider fails before any call. Both `llm-bridge-claudecode` and `llm-bridge-codex` implement `-oneshot`. `organization_id` is a principal-store group the caller must belong to unless it is an administrator or the service token. `checkOperationGrant` reads grant-store's `can_run_operation` on `operation_type`, lenient or strict by `operations.grant_enforcement`; grant-store checks an `operation_type` id against `GET /operation-types`, which is why that route is open. **Budgets are list-price dollars** (`ModelListPrice` from model-store; cache tokens at the input price): an organization's monthly limit (`/operation-budgets`, operator routes, UTC months) and the root intent's `maximum_cost_usd`, the lower winning. An executor calls `SpendingAllowance` before each model call and `RecordModelCall` after, which writes the receipt's usage and the `operation_spend` ledger in one transaction. Not built yet: capabilities, retention.

## The grant gate: can_dispatch_on and can_run_as

`checkPrincipalMayRunHere` (`internal/server/grant_gate.go`) is where grant-store's `can_dispatch_on` and `can_run_as` are enforced: a session started as a principal may start only on an instance, or an instance of a machine, that the principal's grants name, and only as an agent they name. **Lenient by the operator's choice:** a principal holding no grant of a relation is not restricted by it, so a default principal set before any grant exists locks nothing out; a principal holding any grant of a relation is refused outside it. A grant-store that cannot answer is an error — a session that named a principal must not start because the check failed. The gate runs twice on purpose: at `POST /sessions`, so the caller gets the refusal with its reason, and again at spawn, so a session created before its principal's grants changed is judged against the grants as they are now. `grantGateStatus` maps the failure: `ErrNotGranted` → 403 `not_granted`, naming what the grants do allow; an unknown principal → 400 `unknown_principal`; anything else → 502 `grant_store_unavailable`. A session's `agent_id` is agent-store's slug today while a grant names its numeric id, so the slug is resolved through the in-process agent-store; a slug that will not resolve is a refusal, not a pass. Skills are not enforced: a `can_use` grant on a skill is stored and nothing reads it.

## The host prompt every harness receives

At start `syncPromptHarnessDeliveries` (`internal/server/prompt_context.go`) records a `prompt_harness_deliveries` row for every harness in `msg.AllHarnesses` that has none, and touches no row that already exists: agent-store refuses to resolve a prompt for a harness with no row, so a harness added to `msg.AllHarnesses` gets one on the next start. `harnessesThatReadTheirOwnPromptFile` is only the seed — `claude_code` and `jig` read `CLAUDE.md` themselves (jig launches the `claude` binary), everything else is injected — and **the row is the truth after that**, edited on the Files page. `injectPromptContext` puts the host prompt, the prompt of every project collection the session's working directory sits in, and the **context sections its card's tags select** into `HarnessConfig`; agent-store decides what that is per harness, giving a harness that reads a rendered file only the collections that file does not already carry, so no harness gets the same text twice and none gets less than the others. The working directory is the spawn's own (`harness.WorkingDirForSession`: session, then instance, then machine) — until 2026-09-21 this read it from `DisplayName`, so an injected harness whose directory came from those fields got no repo prompt. **The key follows the delivery row**: an `inject` harness gets `system_prompt`, a `native_file` harness gets `append_system_prompt` — Claude Code maps `system_prompt` to `--system-prompt`, which replaces its default prompt. A caller that set `system_prompt`, or the key this would write, wins. A session's `card_id` (checked with kanban-store at create: 400 `unknown_card`, 502 `kanban_store_unavailable`; carried to forks and subagents) is read for its tags at **every** spawn (`kanbanclient.CardTags`), so a tag added to a card reaches the next spawn; a card that cannot be read logs an ERROR and the session starts without its context, like a failed prompt resolution. jig reads neither key — it takes its prompt from its YAML profile — so jig sessions get no injected text. The mutation is in memory and not persisted, so an edit to the prompt takes effect on the next spawn. A held prompt drift that adds sections gets its tags from one single-shot call on `LLMBRIDGE_PROMPT_DRIFT_TAGGER_INSTANCE` with `LLMBRIDGE_PROMPT_DRIFT_TAGGER_MODEL` (`prompt_drift_tagger.go`); it **proposes tags only** — a section's title is its heading — and an empty instance turns labelling off, leaving drifts detected and held, unlabelled.

## The effective-config view

`GET /sessions/{id}/effective-config` answers for a stored session and `GET /effective-config?harness=…&instance_id=…&principal_id=…&agent_id=…&bundle_id=…&board_id=…&card_id=…&tag=…` for one that does not exist yet (`internal/server/effective_config.go`). Both return `msg.EffectiveConfig`: eleven settings — model, effort, max_budget, disabled_tools, permission_mode, principal, instance, agent, bundle, tools, context — each with the layer that decided it, the record it is stored in and one sentence of detail, plus `warnings` naming what would refuse a spawn. The eleven layers, narrowest first, are `session`, `request`, `tag_rule`, `board`, `bundle`, `grant`, `instance`, `harness_default`, `global`, `registry` and `none`, and the legend travels in the answer. **It reports and decides nothing** and it reads the spawn's own code (`resolveToolOffer`, `resolveModelSelection`, the grant gate's reads), so the view cannot say one thing while the spawn does another; keep it reading that code rather than re-deriving a setting here. A dry run with `board_id` reads kanban-store's effective defaults through `kanbanclient.EffectiveDefaults` — needs `LLMBRIDGE_KANBAN_STORE_URL`, else 503 `kanban_store_not_configured`, and 502 `kanban_store_unavailable` when the store will not answer — and fills in whichever of principal, agent, instance and bundle the caller left empty, exactly as the dispatcher would, attributing each to `board` or `tag_rule`. A principal still empty is then filled from `bridge-prefs.default_principal_id`, as the chat pane does, and the answer says so. **Model, effort, spend ceiling and disabled tools are decided once, at `POST /sessions`, by one precedence: the session's own value, then its bundle, then the per-harness default in bridge-prefs** (and for the model only, model-store's `default` role as the floor). `snapshotSessionDefaultsIntoSession` (`internal/server/session_defaults.go`) resolves the bundle once, pins each winner into the row, and records the layer that decided it — the model's in `harness_config.model_selection` (`selected_by` is `session`, `bundle`, `prefs` or `role`), the other three in `harness_config.setting_layers` — so a later change to a bundle or to the harness defaults does not move a session that exists, and the view reads the record instead of guessing. A bundle names a model and an effort and nothing else. A sent `max_budget: 0` and a sent empty `disabled_tools` are the creator's answers and outrank a default; an absent one takes it. `POST /sessions/{id}/config` relabels what it changes as the session's own. A bundle that cannot be resolved refuses the create (422 `model_unresolvable`), as the spawn would have. Until 2026-09-18 only the chat pane applied the harness defaults, by copying them into its own request, and nothing applied a bundle's model or effort — so a dispatched session ran with no ceiling at the harness's own effort whatever its board's bundle said. The chat pane still sends what its controls show, which reads as the session's own. A dry run pins what create would for a creator who names none of the four, which is what a dispatcher sends.

## GET /hook-options

`GET /hook-options` serves what a hook editor must not hardcode: the harnesses the spawn actually wires hooks into, read from `hookConfigKeyByHarness` — `claude_code` under `settings`, `codex` under `codex_hooks`, held to `injectHookSettings` by a test — each with its known events from `harnessHookEvents` and the help text for its matcher syntax, and the scope kinds narrowest first (`session`, `instance`, `global`). `harnessHookEvents` is the same map `GET /harnesses` already serves as `hook_events`, so there is one list and not two; add a harness's events there and both routes follow. bridge-ui's `/hooks` page is the consumer, and it marks a hook stored for a harness this answer does not name as one that never runs.

## The service inventory

`GET /services` joins healthcheck's status (`LLMBRIDGE_HEALTHCHECK_URL`) to each service's processes and the SQLite files they hold open. Processes are found in `/proc` — a systemd check by the cgroup its processes sit in, an HTTP check by the process listening on the URL's port — and **never through DBus**, which the unit has no session for. `GET /services/databases/schema` and `GET /services/databases/rows` open one such file with `mode=ro` and `query_only`, so nothing on this path can write, and **only a file some watched service holds open right now can be read**; anything else is 404. A column whose name looks like a credential comes back masked (`internal/serviceinventory/mask.go`): the name is split on `_`, `-`, `.` and camelCase boundaries and each word matched against a list, so `api_key`, `apiKey`, `refresh_token`, `client_secret`, `password_hash` and `runner_token_hash` are masked while `max_tokens`, `input_tokens`, `keyword` and `session_key` are not. **Bare `key` is deliberately not enough** — across every live database on this host it names a lookup key far more often than a secret — so it masks only beside a qualifier: api, access, private, secret, signing, ssh. All three routes are operator-only.

# Access and operations

## Unit, listen address and required settings

The unit is a **system** unit, `/etc/systemd/system/llm-bridge.service` — not a user unit, so `systemctl --user cat llm-bridge.service` finds nothing. It runs as `kayushkincom` with `ExecStart=/usr/local/bin/llm-bridge`. Drop-ins live in `/etc/systemd/system/llm-bridge.service.d/`: `local.conf` is readable by root only, `oom.conf` sets the OOM policy, and `principal-gating.conf` sets `LLMBRIDGE_PRINCIPAL_STORE_URL`, `LLMBRIDGE_KANBAN_STORE_URL` and `LLMBRIDGE_GRANT_STORE_URL` and loads `EnvironmentFile=~/.config/principal-gating-tokens.env`. It listens on `LLMBRIDGE_LISTEN_ADDR`, `:8160` on every interface. Five settings are **required at startup** and a missing or too-short one is a startup error naming the variable: `LLMBRIDGE_DEMO_LOGIN_SIGNING_KEY` (at least 32 bytes), `LLMBRIDGE_SERVICE_TOKEN` (at least 32 bytes), `LLMBRIDGE_PRINCIPAL_STORE_URL`, `LLMBRIDGE_KANBAN_STORE_URL` and `LLMBRIDGE_GRANT_STORE_URL`. `config.ValidateRequestAuthorizationSettings` is the whole check and `main` refuses to start on it, while `server.New` panics on the two credentials alone — so no code path builds a server that gates nothing while looking gated. **Every environment variable this process reads is declared once**, in `internal/config/settings.go` (`SettingDefinitions`): key, variable, kind (`wiring`, `path`, `secret`, `behaviour`), type, default and what it changes. `config.Load` reads `Config` through that list with llm-bridge's `servicesettings` package and **stops the process** on a value that does not parse as its type and on a set `LLMBRIDGE_` variable nothing declares — both used to pass in silence, the first as the default and the second as a misspelling that did nothing. `TestEveryEnvironmentVariableTheServerReadsIsDeclared` holds every `os.Getenv` in the repo to the list, so add the declaration with the read. `GET /settings` (operator route) describes the server from it — each value in force and whether the environment, the stored record or the default decided it; a secret says only that it is set — and `PUT /settings/{key} {"value":…}` changes a **stored behaviour setting** with no restart: `signal_classifier.model`, `.instance`, `.timeout`, `.maximum_characters`, `.opt_out_harnesses`, `prompt_drift_tagger.instance`, `.model`, `session.idle_timeout` and `session.pty_idle_timeout`. Those nine live in table `service_settings` of the bridge database; the environment seeded each row once, on the first start after 2026-09-18, and **the row is now the only source — setting the variable does nothing**, and the description says so in a note. An instance setting is checked with harness-store on write (400 unknown or disabled, 502 when it cannot answer). Read a stored setting at the time of use with `s.settings.String(config.Setting…)`, never from `s.cfg`: `Config` holds the value the process started with. Wiring, paths and secrets change only in the unit and its drop-ins (409 on a `PUT`). Defaults for addresses are in `internal/productiondefaults`.

## The server's own secrets never reach a child process

`config.SecretEnvironmentVariableNames` lists every variable that must never reach a process this server spawns, and `internal/childprocessenv` strips them from each harness child. A harness child runs an agent that can execute shell commands, so whatever is in its environment the agent can read: the demo login signing key would let it mint a login cookie for any principal, the service token would make it the unrestricted internal caller, and a store service token would let it bypass that store's per-principal enforcement. The four are `LLMBRIDGE_DEMO_LOGIN_SIGNING_KEY`, `LLMBRIDGE_SERVICE_TOKEN`, `GRANT_STORE_SERVICE_TOKEN` and `KANBAN_STORE_SERVICE_TOKEN`. ⚠️ **The two store tokens carry the store's own name and have no `LLMBRIDGE_` prefix**: grant-store, kanban-store, dash and the scheduler all read them from one host-local file, `~/.config/principal-gating-tokens.env`, and this unit loads the same file. Reading them under `LLMBRIDGE_`-prefixed names failed twice over — the grant token read as empty, so grant-store answered every spawn-time read with 401, and the real variables were not on the strip list, so every harness child inherited both. The kanban name is taken from `internal/kanbanclient` rather than restated, so there is one spelling read in one place and stripped in another. A new secret goes in the constant block and in `SecretEnvironmentVariableNames` in the same change.

# Working in this repo

## Module, build and deploy

Module `github.com/kayushkin/llm-bridge-server`, Go 1.25, pushing to `github.com/kayushkin/llm-bridge-server`. It builds from plain main clones with **no `go.work`**, and the shared deploy gate refuses a build that reads a sibling tree on a side branch — so fix the sibling rather than adding a `GOWORK` file. Deploy only with `./deploy.sh` from the main clone on the default branch. It runs `~/bin/deploy-gate check` first, then re-execs itself inside a transient systemd unit under `system.slice`: an agent deploying from inside a bridge session sits in the service's own cgroup, `sudo systemctl stop llm-bridge.service` would take the deploy down with it, and `setsid nohup` does not escape a cgroup kill. The detached run logs to `~/.cache/llm-bridge-deploy.log`, which is under `$HOME` because a transient unit gets a private `/tmp`. ⚠️ **The deploy stops and restarts the service, killing every live bridge session including the deploying agent's own** — background subagents die with it, so finish or wait for them before deploying, and read the outcome from the log after the session resumes.
